# Публикация в main

Правила: `docs/development/DELIVERY_PIPELINE.md`, раздел «Ветки».

## dev → main — только по слову пользователя

1. В своей папке: `git fetch && git merge --ff-only origin/dev`. Строка `shared main` в `python3 tools/pipeline.py status` покажет, сколько доставок не опубликовано.
2. Если в `main` есть чужая работа — сначала принять её (раздел ниже).
3. Основная папка должна стоять на текущем `dev`. После `rollback` — сначала `pipeline.py sync-main`.
4. `python3 tools/pipeline.py publish [--notes <файл с саммари>] [--probe "…"]`. С `--dry-run` скрипт только печатает текст PR. Проба по желанию: `{main}` — путь основной папки.
   - Скрипт проверяет, что `main` влита в `dev`.
   - Открывает PR `dev → main`, сливает его, ставит метку `v<версия>`, подтягивает `dev`.
5. Если PR привязался к чату (`ccd_pr` `get_status`), после слияния отвяжи его (`unbind_pr`).
6. Пользователю: версия, ссылка на PR, что вошло — коротко и по-человечески.

Прямой push в `main`, `--force` и удаление `dev`/`main` запрещены — их останавливает pre-push hook.

## main → dev — чужая работа

1. В своей папке `python3 tools/pipeline.py merge-main`: сливает `origin/dev` и `origin/main`, печатает, что пришло, и команду доставки.
2. Конфликты в чужом арте и файлах — по умолчанию сторона владельца, спроси его.
3. Доставь напечатанной командой (`deliver … --message …`) в фоне. Пробу выбери по тому, что пришло (скил `vba-deliver`).
4. Сообщение для сведения — чатам, чьи зоны задела пришедшая работа.
